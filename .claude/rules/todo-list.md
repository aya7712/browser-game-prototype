# TODOリストルール

## 目的

実装フェーズに入る前に、設計ドキュメント全体から実装タスクを洗い出し、
動作確認可能な単位に分解して一覧化する。
設計ドキュメントではなく、作業セッション中の進捗管理が目的。

## ファイル規則

- **保存先**: `docs/iteration/`
- **ファイル名**: `todo_impl_phase<N>.md`（例: `todo_impl_phase1.md`）
- `docs/iteration/` 以下のファイルは設計ドキュメントではない。実装完了後は削除してよい。
- 設計変更が生じた場合は設計ドキュメントを更新した後に TODOリストも更新する（TODOリストを先に変えない）。

## タスク分解のカテゴリと順序

以下の順序・カテゴリで必ずリストアップする。

### 1. 共通Reactコンポーネントパーツ
複数のシーンで使い回す汎用 UI パーツ（Button・Modal・StatusBar など）。
他のカテゴリから参照されることが多いため、最初に洗い出す。
**型定義はコンポーネント内に書かない。** 後続の「1-B」でデータ層の型に差し替えるため、
Storybook のダミーデータとして使うローカル型のみ許容する。

### 1-B. 共通コンポーネントのデータ層対応
セクション1のコンポーネントが仮定義した型を、2-A完了後にデータ層の型へ差し替える。
対象：コンポーネント内に `export type` / `export interface` として書いたゲーム型（`CropKind`・`ItemKind`・`SeedResult` など）。

### 2-A. 基盤・データ層
シーンUIや Phaser 実装が依存する共有型・マスターデータ・基盤クラスを先に実装する。
必ず含めるタスク：
- `src/game/types.ts` — ゲーム全体で使う共有型（`CropKind`・`ItemKind`・`SeedResult` など）
- `src/game/ecs/components/` — Component 型定義（`component-types.md` に基づく）
- `src/game/data/` — 静的マスターデータ（`items.ts`・`crops.ts`・`recipes.ts` など）
- `src/game/ecs/world.ts` — ECS World クラス
- `src/game/SaveManager.ts` — セーブ・ロード

### 2. シーンごとのReactコンポーネント（UIオーバーレイ）
各シーンに対応する React UI コンポーネント（`TitleUI`・`FarmUI`・`DungeonUI` など）。
`ui-spec.md` の「Phaser/React」列が React の要素をまとめたもの。
**2-A 完了後に実装する。** データ層の型・マスターデータを直接インポートして使う。

### 3. Phaserシーン
各シーンの Phaser 実装（背景描画・BGM・`current-scene-ready` emit）。
Boot と Preloader は既存ファイルの改修として記載する。

### 4. 機能ごとの実装
動作確認可能な単位に細分化した実装タスク。以下の粒度を目安とする。
- 1タスク = 実装して即座にブラウザで確認できる変化があること
- 例: 「タイトル→農場への遷移」「WASD でキャラクターが移動する」「アイテム使用で種が入手できる」

サブカテゴリはアルファベット（4-B, 4-C, …）で分ける（4-A は廃止。基盤・データ層は 2-A に移動）。

## 各タスクの必須フィールド

| フィールド | 必須 | 内容 |
|---|---|---|
| タスク名 | ○ | 実装するもの（コンポーネント名・System 名・機能名） |
| 概要 | ○ | 何を実装するか（ファイルパス・props・EventBus イベントなど） |
| 動作確認ポイント | 機能タスクのみ | 「何が見えれば / 何が起きれば完了か」を1行で記述 |
| 状態 | ○ | `[ ]`（未着手）または `[x]`（完了） |

## 進捗の更新ルール

- タスクに着手したら、実装**完了後**に `[ ]` → `[x]` に更新する。
- 途中で設計変更が判明した場合は、設計ドキュメントを更新してユーザー承認を得てから TODOリストを修正する。
- 新たに必要なタスクが判明したら、その場で末尾に追加してよい（ユーザー確認不要）。
